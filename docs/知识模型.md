## 一、项目需求
定位：
目的：三元组（实体A，关系，实体B）-文档能对应起来，以实现证据溯源
数据情况：
（1）对已有准确知识图谱（knowlede console上直接能导出三元组的数据），gold关系：图谱里已存在的edges，回标到文本
（2）根据ontology定义（只有类型schema，没有实例图谱），按ontology定义，从文本抽取出关系。

## 二、数据层面
### 注意点
（1）防泄露，train和validation层面防泄漏；
（2）数据长度，各长度切分；小样本实验：长度要和训练预算匹配，否则引入阶段噪声。训练前可以先做length审计，超长的报错/丢弃。

### 数据抽取prompt
图谱抽取提示词完整列表（麦麦e学-graph-1.0）
由 rebuild/ontology_prompt.py 生成。设计原则：

SYSTEM 稳定、与本体无关：只约束输出格式与 JSON body 结构，不含任何实体/关系类型清单，换本体无需改动，便于泛化。
USER 承载本体特定内容：实体类型（含每个属性的 name/type/required/描述）、关系类型及其 source/target 端点约束，全部在此动态生成。
校验由 common.ontology() 回退逻辑从 USER 的类型清单重建 schema 完成。
一、SYSTEM PROMPT（稳定模板，与本体无关）
字符数：1368

text
你是一位信息抽取专家。根据用户提供的本体定义和文档内容，从文档中抽取实体和关系。

要求：
1. 只抽取本体中定义的实体类型和关系类型，不要发明新类型
2. 尽量根据文档内容填充实体属性，属性含义见本体中每个属性的说明；没有依据的属性留空，不要编造
3. 关系的 source/target 实体类型必须符合本体中的约束
4. 同一实体在文档中多次出现时，使用相同的 id
5. 实体 id 格式: e1, e2, e3...
6. 如果文档中没有足够信息确定某个实体或关系，不要强行抽取
7. 同一现实实体的全称、简称、缩写和别名只能输出一个实体；优先使用文档中最完整、最正式的名称

请严格按照下方的输出格式与样例输出。

【核心输出规则 — 不可违反】
1. 每个实体必须包含 "id"、"name"、"type" 三个字段，缺一不可。name 必须是非空字符串。
2. 如果某个概念更适合作为其他实体的属性（如数值、状态、标签），请将其填入父实体的 properties 中，不要创建独立实体。
3. 关系的 source_id 和 target_id 必须引用本次输出中已定义的实体 id，不能引用不存在的 id。
4. 只使用下方列出的实体类型与关系类型，不要新增字段或类型。
5. 实体 id 使用简短递增格式: e1, e2, e3...，不要使用其他命名格式。
6. 只输出有充分文本证据支持的实体和关系，不要推测或虚构。

[输出格式要求] 只返回一个 JSON 对象，不要 Markdown、代码块、解释或多余文字。顶层必须且只包含 entities 和 relations 两个数组。
每个实体对象的字段：id、name、type、properties。其中 type 只能取【用户提供的本体】中列出的实体类型；properties 是对象，键取自该实体类型定义的属性，没有依据就留空 {}。
每个关系对象的字段：source_id、target_id、type、properties。其中 type 只能取本体中列出的关系类型，且 source/target 所指实体的类型必须满足该关系在本体中声明的端点约束；source_id/target_id 必须引用本次输出里已定义的实体 id。
下面是输出结构样例（类型名与属性名以用户提供的本体为准，此处仅示意结构）:
{
  "entities": [
    {
      "id": "e1",
      "name": "实体A",
      "type": "类型1",
      "properties": {
        "属性名": "属性值"
      }
    },
    {
      "id": "e2",
      "name": "实体B",
      "type": "类型2",
      "properties": {}
    }
  ],
  "relations": [
    {
      "source_id": "e1",
      "target_id": "e2",
      "type": "关系类型",
      "properties": {}
    }
  ]
}

## 三、算法层面
（1）SFT loss口径：默认整条序列算loss（含prompt+那段超长schema/ontology定义）。system + user prompt巨长（光schema就占大量token），整条算loss会让模型的梯度被prompt主导，真正该学的answer信号被稀释。—— 可以completion-ony只在答案上算loss，信号干净。
（2）训练/推理/评测用的prompt要保持一致。

（3）训练的时候，要记录rollout。

### CPT阶段
数据长度分桶，分桶以后，分别按数据长度训练2k、4k、8k、64k模型；训练当前阶段需要加入上一阶段的数据，防止灾难性遗忘。eg：4k的model是继承2k的best和2k+4k的所有数据。


### SFT阶段
可以用小样本做过拟合测试，来看模型是否具备基本的学习能力。


### GRPO阶段
（1）要细看里面对每个答案的打分，有可能就是多个打分机制之间互相权衡，在一堆错的里面挑了一个相对分高的。
（2）数据量要一点点增加：从50-100-200，后面再全量。
（3）实体抽取：漏抽 + 实体边界/标注粒度不一致。长文本加剧。

（4）实体存在别名问题：别名无法保罗全部别名，采用“种子映射 + 规则泛化 + 未知回退”。
