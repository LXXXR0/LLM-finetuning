# MCD 大模型微调项目 — 学习笔记

## 项目一句话总结

训练一个 AI 助手：记住麦当劳内部知识 → 理解用户问题 → 选择最合适的 Agent 回答。

---

## 核心概念

### SFT（Supervised Fine-Tuning，监督微调）

- **是什么：** 一种训练策略——给模型看"标准答案"，让它模仿
- **类比：** 老师给你答案，你照着抄
- **优点：** 快、稳定
- **缺点：** 模型只会模仿，不会思考

### LoRA（Low-Rank Adaptation，低秩适配）

- **是什么：** 一种参数更新方式——只改模型一小部分参数（约 0.1%）
- **类比：** 不重新装修整栋房子，只换几个关键家具
- **注意：** LoRA 不属于 SFT，它是独立的技术。SFT 和 GRPO 都可以搭配 LoRA 使用
- **关系图：**
  ```
  训练策略（怎么教）：SFT / GRPO
  参数更新（改哪里）：LoRA / 全量微调
  
  本项目 = SFT + LoRA（大部分阶段）
         = GRPO + LoRA（RL 阶段）
  ```

### GRPO（Group Relative Policy Optimization，组相对策略优化）

- **是什么：** 一种强化学习训练策略——让模型自己尝试，用奖励函数打分引导
- **类比：** 老师不给答案，让你自己做，做对了给奖励，做错了扣分
- **优点：** 模型学会思考和推理
- **缺点：** 慢、不稳定、需要精心设计奖励函数

### 三者关系

| 概念 | 维度 | 回答的问题 |
|------|------|-----------|
| SFT | 训练策略 | "怎么教模型" |
| GRPO | 训练策略 | "怎么教模型" |
| LoRA | 参数更新方式 | "改模型的哪些参数" |

## Transformer 模型结构

大模型由很多层叠起来（Qwen3-8B 有 32 层），每层有两个核心部分：

### 注意力层（q/k/v/o_proj）— "看哪里"

用图书馆找书来类比：

| 组件 | 全称 | 类比 |
|------|------|------|
| Q (Query) | 查询 | 你的"找书需求" |
| K (Key) | 键 | 每本书封面的"标签" |
| V (Value) | 值 | 书里的"实际内容" |
| O (Output) | 输出 | 读完后写的"总结" |

工作流程：Q 和所有 K 比对 → 找到最匹配的 → 取出对应 V → 通过 O 整合输出

### 前馈层（gate/up/down_proj）— "怎么想"

用厨房来类比：

| 组件 | 类比 |
|------|------|
| up_proj | 把食材摊开在案板上（升维展开） |
| gate_proj | 厨师判断哪些食材要用（门控过滤） |
| down_proj | 把做好的菜装盘（降维压缩） |

### 为什么 LoRA 改这 7 个模块？

这 7 个就是每层所有的核心计算模块。都加 LoRA = 模型既能学会"看新东西"，也能学会"用新方式思考"。

## 训练相关概念

### Epoch vs Step

| 概念 | 含义 |
|------|------|
| Epoch | 把所有训练数据完整看一遍 |
| Step | 模型参数更新一次 |
| Batch | 每次看几条数据 |

**公式：**      
```
每个 Epoch 的 Steps = 总数据量 ÷ (batch_size × gradient_accumulation × GPU数)
```

### 过拟合

- **是什么：** 模型把训练数据"背"下来了，遇到新问题就不会了
- **类比：** 学生背了课后习题答案，换个问法就懵了
- **防止方法：** weight_decay、LoRA 本身、数据打乱、早停

### 梯度累积（Gradient Accumulation）

- **问题：** GPU 显存不够，一次只能放 1 条数据，但 batch=1 训练不稳定
- **解决：** 累积 4 次梯度再更新一次参数，等效 batch=4
- **类比：** 攒够 4 道题的经验再总结一次，比做一道总结一次更靠谱

### 学习率（Learning Rate）

- **是什么：** 每次更新参数的"步子大小"
- **太大：** 学崩了（参数乱跳）
- **太小：** 学不动（收敛太慢）
- **规律：** SFT 用较大（1e-4 ~ 2e-4），RL 用很小（5e-6），后续阶段比前面小

### 4-bit 量化

- **是什么：** 把模型参数从 16-bit 压缩到 4-bit
- **效果：** 显存需求降低 4 倍（14B 模型从 ~28GB 降到 ~7GB）
- **代价：** 精度略有损失

## 项目六个阶段

### 阶段一：基础 SFT

```
知识库 CSV → data_trans.py → train.csv → sft_training.py → lora_model/ → inference.py
```

**核心流程：** 加载模型 → 配置 LoRA → 准备数据 → 训练 → 保存 → 推理

### 阶段二：知识续训（Continue Pretrain）

```
MD 文档 → 按 token 长度分桶(2k/4k/8k/64k) → 分阶段递进训练 → 知识召回评估
         → GPT 生成 QA 对 → QA 微调
```

**核心思想：** 先让模型"记住"文档，再教它"表达"（回答问题）

**为什么分阶段：** 循序渐进，先学短文档再学长文档，避免一上来就消化不了导致"瞎说话"

**评估方法：** 给模型看文档前半段，让它续写后半段，对比相似度（BLEU/ROUGE）

### 阶段三：Agent 选择（两步 SFT）

```
Step 1: 问题 + Agent信息 → 学会为每个 Agent 生成回答 → q_lora_model/
Step 2: 问题 → 学会排序 4 个 Agent + 置信度 → lora_model/
```

**两步训练的设计哲学：先让模型"理解每个专家的能力"，再教它"选择哪个专家"。**

为什么不能一步到位？如果模型连每个 Agent 擅长什么都不知道，让它排序只能死记硬背，换个问法就不会了。

**关键设计：**
- Step 2 加载 Step 1 的模型（模型接力）
- Step 2 学习率更小（1e-4 vs 2e-4），避免破坏 Step 1 学到的东西（灾难性遗忘）
- 使用自定义 XML 标签做结构化输入输出，方便解析

### 阶段四：强化学习（GRPO）

```
q_lora_model → GRPO 训练（4 个奖励函数）→ rl_lora_model/
```

**核心机制：**
1. 每个问题生成 4 个不同回答
2. 用奖励函数给每个回答打分
3. 好的回答强化，差的回答抑制

**奖励函数设计原则（递进式）：**
- 格式对了 → 小分（基本合格）
- 数量对了 → 中分（方向正确）
- Top-1 对了 → 大分（核心目标）
- 全对了 → 最大分（完美）
- 部分正确也给分（否则模型学不动）
- 惩罚要轻（-1 到 -3），奖励要重（+5, +8）

**关键参数差异：**
- temperature=1.0（高随机性，鼓励探索）
- learning_rate=5e-6（比 SFT 小 40 倍，RL 梯度噪声大）

### 阶段五：进阶技术

```
q_lora_model → Warmup SFT → GRPO(6 奖励) → OPSD 自蒸馏
```

#### Warmup（热身）

- **解决什么：** RL 冷启动——模型不知道输出格式，生成全是乱码，奖励全是负分，学崩了
- **怎么做：** 用 100 条数据做 3 个 epoch 的轻量 SFT，让模型至少知道格式
- **类比：** 先教基本运球姿势，再让他上场比赛

#### 6 个奖励函数（比阶段四更全面）

1. 格式强约束（必须严格正确）
2. 排序准确性（重点 Top-1 + 多样性惩罚防偷懒）
3. 置信度降序（逻辑合理性）
4. 置信度数值准确（不仅排序对，数值也要对）
5. 输出多样性（防止总是输出同一个 Agent）
6. 调试打印（不影响训练）

#### OPSD 自蒸馏

- **解决什么：** GRPO 后仍有少数错误案例
- **核心思想：** 教师和学生是**同一个模型**的两种模式
  - 学生：只看问题 → 可能做错
  - 教师：看问题 + 看正确答案 → 基本能做对
  - 训练目标：让学生的输出接近教师的输出
- **只用错误样本训练**，避免"好的地方被改坏"
- **EMA 教师：** 教师参数 = 0.999 × 旧教师 + 0.001 × 当前学生（平滑平均，更稳定）

### 阶段六：部署

```
LoRA 权重 → 合并到基座模型 → vLLM 启动推理服务 → HTTP API 调用
```

- **LoRA 合并：** 把 LoRA 适配器融入基座模型，变成一个完整文件（不是多个模型合并）
- **vLLM：** 高性能推理引擎，把模型变成 HTTP API 服务
- **线上 temperature=0.1：** 要稳定确定的结果（训练时 1.0 是为了探索）

## 关键设计决策总结

| 决策 | 原因 |
|------|------|
| 用 LoRA 而不是全量微调 | 省显存，14B 模型也能在单卡上训 |
| 续训用 16-bit，SFT 用 4-bit | 续训要精确记忆，SFT 对精度要求低 |
| 续训 LoRA rank=128，SFT rank=32 | 续训要记住大量文档，需要更大容量 |
| 两步训练而不是一步 | 先理解再决策，泛化能力更强 |
| Step 2 学习率比 Step 1 小 | 避免灾难性遗忘 |
| RL 前做 Warmup | 避免冷启动崩溃 |
| Warmup 只用 100 条数据 | 太多会过拟合到 SFT 模式，失去探索能力 |
| RL 学习率极小（5e-6） | RL 梯度噪声大，步子太大会学崩 |
| 奖励函数递进式设计 | 让模型能逐步学习，而不是"全对才有分" |
| OPSD 只用错误样本 | 避免改坏已经做对的部分 |
| 线上 temperature=0.1 | 要稳定输出，不要随机性 |

## 常见问题

### Q: 显存不够怎么办？
- 减小 batch_size
- 增大 gradient_accumulation_steps（等效 batch 不变）
- 用 4-bit 量化
- 减小 LoRA rank

### Q: 模型输出乱码/格式不对？
- 检查 chat template 是否正确
- 检查训练数据格式是否一致
- 可能需要更多训练轮数

### Q: RL 训练 reward 一直是负数？
- 模型可能不知道输出格式 → 先做 Warmup
- 奖励函数可能太严格 → 加入部分奖励
- 学习率可能太大 → 降低到 1e-6 ~ 5e-6

### Q: 训练 loss 不降？
- 学习率可能太小 → 适当增大
- 数据可能有问题 → 检查几条样本
- 模型可能已经收敛 → 正常现象
